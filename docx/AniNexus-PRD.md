## 1. 文档目的

本文档用于统一 AniNexus 的产品范围、功能模块、技术边界、研发顺序和验收标准。项目采用阶段门禁方式推进：每个阶段必须完成开发、测试、文档和验收，才能进入下一阶段。

## 2. 产品概述

AniNexus 是面向动漫与漫画爱好者的一站式内容发现和个人管理平台。项目整合：

- `search_manga` 的动漫/漫画数据、搜索、排行榜、详情与推荐能力。
- `OtakuNeko` 的收藏同步、用户画像、AI 对话和 Agent 能力。

首个可交付版本以响应式网站为载体，验证内容检索、收藏管理和 AI 助手三条核心链路；随后建设 PWA，最终通过共享 API、设计系统和业务模型开发移动 App。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 用户可以快速搜索、筛选并查看动漫和漫画信息。
2. 用户可以维护追番、想看、已完成等个人收藏状态。
3. 用户可以通过 AI 助手完成内容查询、推荐和收藏操作。
4. 系统基于用户行为和收藏形成可解释的个性化推荐。
5. Web 与未来 App 共用后端 API、认证协议和核心数据模型。

### 3.2 首期非目标

- 不提供未经授权的漫画正文、动画视频或下载服务。
- 不在首期建设社区发帖、私信和复杂社交关系。
- 不在首期采用 Kubernetes、Kafka、GraphQL 或完整微服务架构。
- 不在 MVP 同时开发原生 iOS 与 Android 客户端。
- 不以 AI 自动生成的内容替代可追溯的结构化内容数据。

## 4. 用户角色

| 角色 | 核心需求 | 首期权限 |
| --- | --- | --- |
| 游客 | 搜索、浏览、查看排行和详情 | 只读访问公开内容 |
| 注册用户 | 收藏、评分、维护观看状态、使用 AI 助手 | 管理个人数据 |
| 管理员 | 数据同步、内容修正、任务与系统状态管理 | 后台管理权限 |

## 5. 核心用户旅程

### 5.1 内容发现

首页进入 → 输入关键词或选择筛选条件 → 查看搜索结果 → 打开详情 → 查看相似推荐 → 收藏或评分。

### 5.2 个人追番管理

登录 → 添加收藏 → 设置“想看/在看/已完成/搁置/弃置” → 更新进度 → 在个人中心查看统计和提醒。

### 5.3 AI 助手

打开助手 → 用自然语言描述偏好或问题 → Agent 调用搜索/详情/推荐工具 → 流式返回带来源的答案 → 用户确认后执行收藏操作。

## 8. 技术架构基线

### 8.1 Monorepo 规划

```text
AniNexus/
├─ apps/
│  ├─ api/                 # FastAPI
│  └─ web/                 # Next.js
├─ packages/
│  ├─ api-client/          # OpenAPI 生成的 TypeScript 客户端
│  ├─ ui/                  # 跨页面设计系统
│  └─ config/              # 共享前端配置
├─ services/
│  └─ worker/              # 异步任务 Worker
├─ infra/
│  ├─ docker/
│  └─ nginx/
├─ tests/
├─ docx/
└─ docker-compose.yml
```

### 8.2 技术选型

- 后端：Python 3.12、FastAPI、Pydantic v2、SQLAlchemy 2 Async、Alembic、`asyncmy`、`uv`。
- AI：LangChain + LangGraph；模型供应商通过适配层接入。
- 前端：Next.js App Router、React、TypeScript、pnpm、Tailwind CSS、shadcn/ui、Radix UI。
- 前端数据：TanStack Query；Zustand 仅保存必要的客户端界面状态；React Hook Form + Zod。
- 数据：MySQL 8.4 LTS 为业务事实源；Redis 用于缓存、限流和任务状态；Qdrant 用于向量检索。
- 异步任务：Celery + Celery Beat。
- 通信：REST `/api/v1`；AI 输出使用 SSE；实时双向业务出现后再引入 WebSocket。
- 网关：开发环境直接访问服务，部署环境使用 Nginx 或 Caddy。
- 可观测性：结构化日志、OpenTelemetry、Sentry；生产阶段接入指标面板。
- 测试：pytest、pytest-asyncio、Vitest、Playwright。
- 质量：Ruff、Pyright、ESLint、Prettier、pre-commit、CI。

项目已选定 Python 3.12.10，并使用该版本创建 `.venv`。依赖声明和 CI 均应以 Python 3.12 为运行基线。

### 8.3 数据边界

- MySQL 是用户、内容、收藏、评分、会话元数据的唯一真实数据源。
- Qdrant 仅保存可重建的向量及检索元数据，不作为业务事实源。
- Redis 中数据默认可过期、可重建，不保存唯一业务记录。
- 外部数据入库前完成来源映射、字段标准化、去重和同步时间记录。

### 8.4 API 规范

- 所有业务接口使用 `/api/v1` 前缀。
- 使用统一成功响应、错误码、分页和时间格式。
- 写接口支持必要的幂等键；危险操作需要权限校验与审计。
- OpenAPI 是前后端契约来源，由它生成前端客户端和接口类型。
- 列表接口限制最大页大小，所有数据库查询避免无界结果集。

## 9. 非功能性需求

### 9.1 性能

- 普通 API 在正常负载下 P95 响应时间目标小于 500 ms（不含第三方接口和 AI 生成）。
- 首屏核心内容在常见移动网络下应优先显示骨架与可交互区域。
- 搜索、排行榜和详情热点数据允许短时缓存。
- AI 首个流式片段目标在 3 秒内返回；超时必须可取消并提示。

### 9.2 安全与隐私

- 密钥只通过环境变量或密钥服务注入，不进入仓库。
- 对输入进行结构校验；数据库访问使用参数化查询。
- 用户隐私数据、令牌和模型请求日志默认脱敏。
- 用户可删除自己的会话、搜索历史和账户数据。
- 依赖、镜像及代码进入 CI 安全扫描。

### 9.3 可访问性与兼容性

- 核心流程满足 WCAG 2.2 AA 的基础要求。
- 全站支持键盘操作、清晰焦点、语义标签和合理对比度。
- 支持主流现代浏览器的最近两个稳定版本。

### 9.4 可维护性

- 领域模块之间通过服务接口通信，禁止跨模块直接依赖内部实现。
- 迁移脚本、测试和 API 文档随功能代码一并交付。
- 日志必须携带请求 ID；异步任务必须携带任务 ID。

## 10. 标准化开发流程

每个功能模块均执行：需求澄清 → 技术设计 → 接口契约 → 数据迁移 → 实现 → 自动化测试 → 代码审查 → 验收 → 文档更新。

### 阶段 0：项目初始化

交付物：

- 创建 `.venv`、Git 仓库、`.gitignore` 和基础说明文档。
- 建立 Monorepo 目录及环境变量示例。
- 配置 Python/Node 包管理、代码格式化、静态检查和 pre-commit。
- 创建 Docker Compose 开发基础设施。
- 建立最小 CI，至少执行 lint、类型检查和单元测试。

完成门槛：全新环境可依据文档启动；CI 全绿；仓库无密钥和生成文件。

### 阶段 1：后端骨架与数据基础

交付物：

- FastAPI 应用工厂、配置、日志、健康检查和统一异常处理。
- MySQL 异步连接、SQLAlchemy 模型基类与 Alembic。
- Redis、Qdrant 连接封装。
- 用户、内容和数据来源的第一版表结构。
- `/api/v1/health` 与 OpenAPI 契约。

完成门槛：容器和本地两种方式均可启动；迁移可正向执行；基础集成测试通过。

### 阶段 2：内容导入、检索与详情

交付物：

- 分析并迁移 `search_manga` 数据与逻辑，不直接复制无边界旧代码。
- 完成内容规范化、来源映射、去重和同步任务。
- 实现列表、搜索、筛选、排行、详情 API。
- 建设首页、搜索结果和详情页。

完成门槛：核心内容链路端到端可用；失败同步可重试；搜索与分页测试通过。

### 阶段 3：认证与个人收藏

交付物：

- 注册、登录、刷新、退出和 RBAC。
- 收藏、观看状态、进度和个人评分。
- 登录注册页与“我的收藏”页面。
- 认证安全、越权和并发写入测试。

完成门槛：用户数据隔离验证通过；关键写操作幂等；核心 E2E 测试通过。

### 阶段 4：AI 助手与 Agent

交付物：

- 从 `OtakuNeko` 提炼可复用的 LangGraph 流程和工具设计。
- 实现会话、SSE 流式输出、搜索/详情工具和引用。
- 加入收藏类写工具的二次确认机制。
- 完成模型适配、超时、重试、成本记录与错误降级。

完成门槛：AI 回答可追溯；工具权限隔离通过；中断、超时和失败场景可恢复。

### 阶段 5：推荐、画像与通知

交付物：

- 基础推荐、偏好标签、推荐解释与反馈接口。
- 异步生成向量和更新用户画像。
- 站内通知与内容更新订阅。

完成门槛：冷启动有合理降级；推荐结果可解释；任务重复运行不会污染数据。

### 阶段 6：管理后台与生产化

交付物：

- 数据同步、内容修正、任务重试和健康状态后台。
- 完整监控、错误告警、备份恢复和部署手册。
- 性能、安全、可访问性和浏览器兼容测试。

完成门槛：预发布环境通过验收清单；备份恢复演练成功；高风险安全问题清零。

### 阶段 7：PWA 与 App

交付物：

- 响应式体验完善、PWA 安装、离线壳和推送。
- 冻结稳定的移动端 API 契约并建立版本兼容策略。
- 评估 React Native + Expo；复用 TypeScript API Client、校验 Schema、设计 Token 和业务规则。
- 实现 App 的登录、首页、搜索、详情、收藏和 AI 对话最小闭环。
- 建立测试分发、崩溃监控、隐私政策和应用商店发布流程。

完成门槛：真机核心流程通过；弱网和离线行为明确；达到应用商店隐私与稳定性要求。

## 11. 迭代与任务管理规范

- 每个迭代只承诺满足“准备就绪定义”的需求。
- 每个需求拆成可独立验证的小任务，绑定需求编号和验收标准。
- 数据模型/API 变更必须先更新设计或契约，再进入实现。
- 分支建议：`main` 保持可发布，功能分支使用 `feat/<module>-<topic>`。
- 提交遵循 Conventional Commits，例如 `feat(search): add filtered content query`。
- Pull Request 必须包含变更摘要、测试证据、数据库影响和回滚说明。

### 11.3 Git 按功能分支开发流程

本项目采用以 `main` 为稳定主分支、以短生命周期功能分支为开发单元的工作流。`main` 必须始终保持可测试、可部署和可回滚；任何功能、修复或重构均不得直接在 `main` 上开发。

```bash
cd AniNexus

git add .
git commit -m "chore: initialize project"

git push -u origin main
```

初始化后应在代码托管平台保护 `main` 分支：禁止强制推送和直接提交；至少一人审查通过且 CI 全部通过后才允许合并。

如果远程仓库已存在，开发者应直接克隆，不要再次执行 `git init`：

```bash
git clone <repository-url>
cd AniNexus
git checkout main
git pull --ff-only origin main
```

#### 11.3.2 分支类型与命名

| 分支 | 用途 | 示例 | 来源 | 合并目标 |
| --- | --- | --- | --- | --- |
| `main` | 稳定、可发布代码 | `main` | — | — |
| `feat/*` | 新功能 | `feat/search-filter` | `main` | `main` |
| `fix/*` | 普通缺陷修复 | `fix/login-token-refresh` | `main` | `main` |
| `refactor/*` | 不改变外部行为的重构 | `refactor/content-service` | `main` | `main` |
| `docs/*` | 仅文档修改 | `docs/git-workflow` | `main` | `main` |
| `test/*` | 测试补充或调整 | `test/library-api` | `main` | `main` |
| `chore/*` | 工具、依赖、构建和配置 | `chore/setup-ci` | `main` | `main` |
| `release/*` | 版本发布准备 | `release/0.1.0` | `main` | `main` |
| `hotfix/*` | 生产紧急修复 | `hotfix/auth-expiry` | `main` | `main` |

分支名统一使用小写英文和连字符，不使用空格、中文或无意义编号。一个分支只处理一个功能或问题，并尽量关联需求编号，例如 `feat/AUTH-01-user-register`。

#### 11.3.3 开始一个功能

开始开发前，先同步最新 `main`，再从它创建功能分支：

```bash
git checkout main
git pull --ff-only origin main
git checkout -b feat/SEARCH-02-content-filter
git push -u origin feat/SEARCH-02-content-filter
```

功能开发顺序：确认验收标准 → 更新接口或数据设计 → 编写实现 → 补充测试 → 更新文档 → 本地验证。不要在同一个功能分支混入无关格式化、重构或其他需求。

#### 11.3.4 日常开发与提交

提交前先检查变更范围：

```bash
git status
git diff
git add <changed-files>
git diff --cached
git commit -m "feat(search): add content filters"
git push
```

提交信息使用 Conventional Commits：

```text
<type>(<scope>): <summary>
```

常用 `type` 包括 `feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`perf`、`build` 和 `ci`。摘要使用简洁的英文祈使句；破坏性变更须在正文中注明 `BREAKING CHANGE:`。提交应小而完整，每个提交都应能通过基本检查，禁止提交密钥、真实凭据、日志、构建产物或本地环境文件。

#### 11.3.5 同步主分支并处理冲突

创建 Pull Request 前，将远程最新 `main` 整合到当前分支。个人功能分支优先使用 rebase，以保持历史清晰：

```bash
git fetch origin
git rebase origin/main
```

发生冲突时，逐个修改冲突文件并验证内容，然后继续：

```bash
git add <resolved-files>
git rebase --continue
```

需要取消本次 rebase 时执行：

```bash
git rebase --abort
```

已推送且仅自己使用的功能分支在 rebase 后使用安全强推：

```bash
git push --force-with-lease
```

多人共用分支不得擅自 rebase 或强推；应先与协作者协调，必要时改用 `git merge origin/main`。

#### 11.3.6 本地质量检查

推送最终版本和创建 Pull Request 前，至少完成：

- 代码格式化、lint 和类型检查。
- 相关单元测试与集成测试。
- 涉及核心链路时执行 E2E 测试。
- 数据库迁移的正向执行验证，以及必要的恢复方案验证。
- 确认环境变量示例、API 契约和相关文档已经同步更新。
- 使用 `git status` 确认没有遗漏文件或意外生成物。

具体命令以项目后续在根目录提供的 `README.md`、任务脚本和 CI 配置为准。本地检查未通过时不得请求合并。

#### 11.3.7 创建 Pull Request

将功能分支推送到远程后，创建目标为 `main` 的 Pull Request。标题建议沿用 Conventional Commits，例如 `feat(search): add content filters`。描述必须包含：

- 关联的需求或问题编号。
- 变更目的和主要实现。
- 明确的非目标或未完成事项。
- 测试命令、结果和必要的界面截图。
- API、数据库、配置、权限和兼容性影响。
- 部署注意事项及回滚或恢复方案。

PR 应保持在可审查规模；若改动过大，应先拆成相互独立且可验证的多个 PR。审查意见处理完毕后，提交者需再次确认 CI 通过且分支未落后于 `main`。

#### 11.3.8 审查与合并

合并门禁：验收标准满足、至少一人批准、所有必需 CI 检查通过、无未解决审查意见、无高风险安全问题。

功能分支默认使用 Squash and merge，使一个功能在 `main` 上形成一个语义清晰的提交。合并提交标题继续遵循 Conventional Commits。不得使用会绕过分支保护或 CI 的方式合并。

合并后删除远程和本地功能分支，并同步本地 `main`：

```bash
git checkout main
git pull --ff-only origin main
git branch -d feat/SEARCH-02-content-filter
git push origin --delete feat/SEARCH-02-content-filter
```

只有在确认 PR 已合并且分支内容不再需要后才能删除分支；`git branch -d` 拒绝删除时应先查明原因，不直接改用强制删除。

#### 11.3.9 版本发布

日常已完成的功能持续合入 `main`。准备版本时，从最新 `main` 创建发布分支，只允许修改版本号、变更日志、发布文档以及发布阻塞缺陷：

```bash
git checkout main
git pull --ff-only origin main
git checkout -b release/0.1.0
```

发布验证通过后，通过 PR 将发布分支合并回 `main`，随后创建带注释标签并推送：

```bash
git checkout main
git pull --ff-only origin main
git tag -a v0.1.0 -m "release: v0.1.0"
git push origin v0.1.0
```

标签必须指向已通过 CI 和发布验收的 `main` 提交。发布完成后删除 `release/*` 分支，并在发布记录中注明数据库迁移、配置变化、已知问题和回滚版本。

#### 11.3.10 生产紧急修复

生产故障需要紧急修复时，从对应生产版本所在的最新稳定 `main` 创建 `hotfix/*` 分支：

```bash
git checkout main
git pull --ff-only origin main
git checkout -b hotfix/auth-expiry
```

只提交解决故障所需的最小改动，同时补充回归测试。紧急修复仍须通过 PR、必要审查和 CI；不得因紧急而跳过安全检查。合并到 `main` 后创建补丁版本标签，例如 `v0.1.1`，完成部署验证并删除 hotfix 分支。

#### 11.3.11 标准功能开发示例

```text
同步 main
  → 创建 feat/SEARCH-02-content-filter
  → 分批实现并提交
  → rebase 最新 origin/main
  → 完成本地质量检查
  → 推送并创建 PR
  → 代码审查与 CI
  → Squash 合并到 main
  → 删除功能分支
  → 按版本计划发布并打标签
```

严禁事项：直接在 `main` 开发或提交、向 `main` 强制推送、合并未通过 CI 的代码、提交密钥或真实生产数据、把多个无关功能塞入一个分支、在未知影响下改写共享分支历史。

### 11.1 准备就绪定义（Definition of Ready）

- 用户价值和使用场景明确。
- 需求范围、非目标及依赖明确。
- 验收标准可测试。
- UI 稿、接口契约或数据设计已达到实现所需程度。
- 安全、隐私和迁移影响已评估。

### 11.2 完成定义（Definition of Done）

- 功能满足验收标准并经过代码审查。
- 单元、集成和必要的 E2E 测试通过。
- lint、格式、类型检查和安全检查通过。
- 数据迁移可执行，重要变更具备回滚或恢复方案。
- API、环境变量和运行文档已更新。
- 无已知阻塞级或高风险缺陷。

## 12. 测试策略

| 层级 | 覆盖范围 | 执行时机 |
| --- | --- | --- |
| 单元测试 | 领域规则、校验、排序、映射和工具函数 | 每次提交 |
| 集成测试 | API、数据库、Redis、Qdrant、异步任务 | Pull Request |
| 契约测试 | OpenAPI 与生成客户端兼容性 | Pull Request |
| E2E 测试 | 登录、搜索、详情、收藏、AI 对话 | 合并前及预发布 |
| 非功能测试 | 性能、安全、可访问性、恢复能力 | 里程碑发布前 |

测试环境使用独立数据库；禁止自动化测试连接生产数据。

## 13. 发布与环境策略

环境分为本地开发、测试、预发布和生产。配置结构一致，凭据和容量不同。

- 本地开发：Docker Compose 启动依赖服务，前后端支持热更新。
- 测试：由 CI 创建隔离环境，使用种子数据。
- 预发布：尽量复刻生产拓扑，用于迁移、性能和验收。
- 生产：滚动或蓝绿发布；迁移前备份；保留明确回滚版本。

版本采用语义化版本。数据库破坏性变更使用“扩展—迁移—收缩”策略，避免一次部署同时破坏旧客户端。

## 14. 核心指标

- 搜索成功率：有搜索行为的会话中，进入详情或收藏的比例。
- 收藏转化率：详情访问到收藏操作的比例。
- 次周留存：新注册用户次周再次使用的比例。
- AI 有效回答率：未报错且用户未立即改写同一问题的对话比例。
- AI 工具成功率和首片段延迟。
- API 可用性、P95 延迟和错误率。
- 同步任务成功率、数据新鲜度和重复数据率。

首个 MVP 阶段先建立指标采集能力，不提前设定缺少基线的数据目标。

## 15. 主要风险与应对

| 风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 两个旧项目模型和字段不一致 | 数据重复、逻辑混乱 | 先定义统一领域模型和迁移映射，再迁移代码 |
| 外部数据源不稳定或授权不明 | 内容缺失、合规风险 | 保留来源、限流和缓存；只接入允许使用的数据 |
| AI 幻觉或误执行写操作 | 用户信任与数据风险 | 检索引用、结构化工具、权限校验和二次确认 |
| Web 与 App 重复开发 | 成本增加 | 共享 API Client、Schema、设计 Token 和业务规则 |
| 过早微服务化 | 交付变慢、运维复杂 | 保持模块边界，在明确扩展压力后渐进拆分 |
| Python 依赖版本漂移 | 本地、CI 和生产行为不一致 | 统一使用 Python 3.12，锁定依赖并在 CI 验证 |

## 16. MVP 验收清单

- 游客能够浏览首页、排行榜、搜索结果和详情。
- 用户能够注册、登录、退出并安全刷新会话。
- 用户能够收藏内容并维护观看/阅读状态和进度。
- AI 助手能够流式回答，并调用内容搜索和详情工具。
- 关键内容展示数据来源；AI 回答中的事实可追溯。
- 核心页面移动端可用，具备加载、空、错误和无权限状态。
- 自动化测试覆盖核心链路，CI 全部通过。
- 项目可由新环境依照文档启动，不依赖开发者机器上的隐式配置。
