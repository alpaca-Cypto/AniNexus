## 二、应用简介（短版）

> 直接粘贴进「应用简介」输入框。

AniNexus 是一个面向中文动漫与漫画爱好者的内容门户与个人追番中枢：公开首页提供新番放送表、条目检索与作品发现，登录后的个人工作区提供收藏库、追番日历、进度管理与更新提醒。

我们希望接入 Bangumi 的 OAuth 2.0 授权，让用户用自己的 Bangumi 账号登录并授权，从而把「在看 / 想看 / 看过」收藏状态、单集进度、评分与短评同步到 AniNexus，免去目前手工导出收藏文件、手工粘贴个人 Token 的繁琐流程。

授权范围上，AniNexus **仅读取发起授权的用户本人的收藏与进度数据**，用于在应用内展示与同步；不读取其他用户的数据，不修改 Bangumi 上的任何内容，不向任何第三方共享或转售数据，也不会将数据用于训练 AI 模型。Access Token 与 Refresh Token 仅在服务端加密存储，用户可在应用内随时解绑，解绑即删除对应凭据。

**为什么需要更稳定的授权方式**：AniNexus 是长期运行的多用户在线服务，个人 Access Token 方案存在凭据泄露风险、有效期短（7 天）且无法按用户隔离。OAuth 2.0 授权码模式让每个用户独立授权、独立存储、独立撤销，既提升安全性，也符合 Bangumi 对第三方应用的规范要求。

## 三、应用简介（详细版）

> 若后台支持填写较长说明，或审核人员要求补充材料，使用此版本。

### 3.1 应用是什么

AniNexus 是一个自建的动漫 / 漫画收藏与追番进度管理服务，由两部分组成：

- **公开门户**：每周新番放送表（Bangumi 日历）、条目检索与详情、相似作品推荐，任何访客无需登录即可浏览。
- **个人工作区**：登录后提供收藏库、追番日历、观看进度、更新提醒与个人画像统计。

目标用户是中文动漫与漫画爱好者。产品定位是「内容发现 + 个人内容中枢」，即在浏览作品的同时，把自己在 Bangumi 的收藏与进度整合到一个统一的看板里管理。

### 3.2 当前方案的痛点

在申请 OAuth 之前，AniNexus 通过两种临时方式获取用户收藏：

1. **手工导入**：用户自行从 Bangumi 导出收藏文件（`bangumi_collection.json`）后上传；
2. **个人 Access Token**：在服务端配置一个长期 Token，仅用于识别账号身份。

这两种方式都不可持续：手工导入数据滞后且体验割裂；个人 Token 无法按用户隔离、有效期短（7 天）、一旦泄露影响全部用户，且不符合第三方应用接入规范。OAuth 2.0 授权码模式正是为解决这类问题而设计。

### 3.3 需要访问的 Bangumi 接口及用途

| 接口 | 用途 | 授权 | 状态 |
| --- | --- | --- | --- |
| `GET /v0/me` | 读取当前授权用户的基本资料（用户 ID、用户名、昵称、头像），用于在 AniNexus 中绑定并展示 Bangumi 账号身份 | 需要 | 已实现 |
| `GET /calendar` | 读取公开的每周番剧放送表，用于首页追番日历 | **无需授权**（公开接口） | 已实现 |
| `GET /v0/subjects/{subject_id}` | 读取作品条目资料（标题、简介、封面、评分、集数等），用于条目详情页 | 授权可选（公开数据） | 计划中 |
| `GET /v0/users/{username}/collections` | 读取授权用户本人的收藏列表（`{username}` 传其 Bangumi 用户名），用于同步收藏库 | 需要（私有收藏） | 计划中 |
| `GET /v0/users/{username}/collections/{subject_id}` | 读取授权用户对单条作品的收藏详情（收藏类型、评分、进度、短评、标签） | 需要（私有收藏） | 计划中 |

说明：

- 请求头统一使用 `Authorization: Bearer <access_token>`，不通过 query string 传递 Token。
- ⚠️ **`GET /v0/me` 的响应包含用户绑定邮箱与注册时间**。AniNexus 只取用其中的用户 ID、用户名、昵称与头像用于展示身份；**邮箱等字段不会被写入数据库、不会展示、也不用于任何其他用途**。特此说明，以便审核时知悉我们确实收到该字段并选择不保留它。
- 接口基地址为 `https://api.bgm.tv`，授权页与换 Token 的基地址为 `https://bgm.tv`（两者不同）。
- **写操作（修改收藏状态、更新观看进度）暂不在申请范围内。** 若后续需要「把进度回写到 Bangumi」，我们会先与 Bangumi 沟通后再单独提出申请。

### 3.4 数据使用与隐私承诺

- **最小必要**：只请求当前登录用户主动授权的数据，不批量抓取、不请求其他用户的数据。
- **邮箱等敏感字段不落库**：`GET /v0/me` 会返回用户绑定邮箱与注册时间，AniNexus 不存储、不展示、不传输、不用于任何用途。
- **只读不写**：当前阶段不修改用户在 Bangumi 的任何数据。
- **不共享**：不向任何第三方提供、出售或交换用户数据；不用于训练 AI 模型；不做广告用途画像。
- **不长期囤积**：同步到 AniNexus 的收藏数据属于用户自己的数据副本，用户删除账号或解绑时一并删除。
- **凭据隔离**：每个用户的 Access Token / Refresh Token 独立存储于服务端数据库，并进行加密；日志中不记录 Token 明文与用户收藏正文。
- **可撤销**：用户可随时在 AniNexus 内解除绑定，也可在 Bangumi 侧撤销授权；两种方式都会立即使本地凭据失效。

### 3.5 安全与实现要点

- 采用 **Authorization Code** 模式，不实现隐式授权，不接触用户 Bangumi 密码。
- 授权请求携带随机 `state` 并在回调时校验，防止 CSRF。
- `code` 有效期仅 60 秒，服务端在回调中立即用 `client_secret` 换取 Token，不落盘、不在前端传递。
- Token 到期（`expires_in = 604800`，即 7 天）时用 `refresh_token` 自动续期，续期失败则提示用户重新授权，不进行循环重试。
- 对 Bangumi 接口异常做降级处理：401 时明确提示「授权失效，请重新登录」，5xx / 超时返回友好错误而不是把上游错误直接抛给用户。
- 公开放送表接口与用户授权**完全解耦**：即使某个用户的 Token 失效，也不会影响其他用户或访客浏览日历。

### 3.6 请求频率与负载

- 放送表（`/calendar`）由服务端缓存后对全部访客复用，避免按访客放大请求量。
- 用户收藏同步采用**增量 + 用户手动触发**，不做后台高频轮询，不为每个用户定时全量拉取。
- 遵守 Bangumi 的频率限制，遇到限流会退避重试而非持续请求。

### 3.7 User-Agent 规范

Bangumi 要求非浏览器请求携带包含**开发者个人 ID** 与**应用名称**的 User-Agent，开源项目还应附上项目主页。

> ⚠️ 当前项目默认值为 `AniNexus/0.1.0 (personal deployment)`，**不符合该规范**（缺少开发者 ID 与主页），上线前需修正。

建议改为：

```text
<你的 GitHub 用户名>/AniNexus/0.1.0 (https://github.com/<你的 GitHub 用户名>/AniNexus)
```

对应环境变量 `BANGUMI_USER_AGENT`（`backend/src/aninexus_backend/config.py` 中的默认值也需同步修改）。

## 四、审核问答准备

**Q：AniNexus 需要写权限吗？会不会修改用户在 Bangumi 上的数据？**
A：当前不需要，也不修改。申请仅为读取本人收藏与进度用于展示同步。若未来需要回写进度，会另行沟通申请。

**Q：Bangumi 的 `scope` 参数尚未实现，如何保证只读？**
A：我们知晓该限制，因此把「只读」作为代码层面的强约束，而非依赖平台控制：当前实现中所有授权接口均为 `GET`，不调用任何写接口，也不会传递写入参数。这一点在应用内和隐私说明中都会向用户明示。

**Q：是否会把用户数据交给第三方或用于 AI？**
A：不会。站内 AI 助手为独立模块，不接入 Bangumi 用户数据用于训练或推理；用户数据不对外共享、不出售。

**Q：`/v0/me` 会返回用户邮箱，你们如何处理？**
A：只读取用户 ID、用户名、昵称与头像用于展示绑定身份，邮箱与注册时间字段不写入数据库、不展示、不用于任何用途。

**Q：多处登录、凭据如何保管？**
A：每个用户独立授权、独立 Token，服务端加密存储，日志脱敏；用户解绑或撤销授权即删除凭据。

**Q：会不会对 Bangumi 造成高频压力？**
A：公开日历全站共享缓存；用户收藏同步为增量、按需触发，不轮询、不批量抓取其他用户。

**Q：这是个人项目还是公开服务？**
A：面向公众的在线服务，计划部署在云端（`https://<你的域名>`），支持任意 Bangumi 用户自行注册并授权。

## 五、申请通过后的对接清单（代码侧待办）

申请下来的 `client_id` / `client_secret` 需要落到代码里，建议按此顺序推进：

1. **配置项**：在 `backend/src/aninexus_backend/config.py` 的 `Settings` 中新增 `bangumi_client_id`、`bangumi_client_secret`（`field(repr=False)`）、`bangumi_redirect_uri`，并在 `backend/.env.example` 与 `compose.yaml` 中补充对应变量。
2. **授权入口**：新增 `GET /api/v1/bangumi/oauth/authorize`，生成随机 `state` 并 302 跳转到 `https://bgm.tv/oauth/authorize`。
3. **回调处理**：新增 `GET /api/v1/bangumi/oauth/callback`，校验 `state` 后以 `authorization_code` 模式向 `https://bgm.tv/oauth/access_token` 换取 Token。
4. **凭据存储**：新增 Token 表（`user_id`、`access_token`、`refresh_token`、`expires_at`），Token 字段加密后落库，替换当前 `Settings.bangumi_access_token` 的单用户全局 Token 方案。
5. **自动续期**：封装 `refresh_token` 模式续期，并在调用前用 `expires_at` 判断是否需要刷新；续期失败清理凭据并置为「未连接」。
6. **状态接口改造**：`GET /api/v1/bangumi/status` 从「读取环境变量 Token」改为「读取当前登录用户的绑定状态」，保留 `configured` / `connected` / `username` 返回结构，前端 `bangumiService.ts` 无需改动。
7. **User-Agent**：把 `BANGUMI_USER_AGENT` 与 `config.py` 默认值改为符合规范的 `<你的 GitHub 用户名>/AniNexus/0.1.0 (https://github.com/<你的 GitHub 用户名>/AniNexus)`。
