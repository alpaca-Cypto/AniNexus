# AniNexus 阶段开发评审与范围收敛建议

> 评审日期：2026-09-15
> 评审范围：当前 AniNexus 前后端、数据迁移方案、开发文档及现有功能状态。

## 1. 总体结论

AniNexus 的产品方向清晰，已经具备“内容发现 + 个人内容中枢”的完整设想，但当前工程范围明显大于项目现阶段的交付能力。

一句话评价：**产品想法很好、前端完成度较高，但工程范围已经失控，需要立即做减法。**

| 维度 | 阶段评分 | 评价 |
|---|---:|---|
| 产品方向 | 8/10 | 发现、收藏、规划和推荐能够形成有价值的用户闭环 |
| 前端观感 | 7/10 | 功能丰富、交互基础较完整，但历史风格和技术体系尚未统一 |
| 后端基础 | 6/10 | 已具备主要业务接口和本地数据库，但长期运行能力仍需补齐 |
| 数据可靠性 | 5/10 | 已确定 Bangumi 主数据方向，但迁移、融合和更新时间仍不完整 |
| 上线成熟度 | 4/10 | OAuth、迁移、缓存、限流、监控和回滚等生产能力尚未闭环 |
| 范围控制 | 3/10 | 同时推进门户、日历、AI、RAG、RSS、角色系统和多数据源，主线不够集中 |

作为个人作品，AniNexus 已明显超过普通练手项目；作为准备公开部署的产品，目前仍属于大型开发中原型。

## 2. 当前最有价值的部分

项目已经形成一条合理的产品路径：

> 发现作品 → 查看详情 → 加入收藏 → 安排追番 → AI 根据收藏提供查询和推荐

主要优势包括：

1. 不只是动漫搜索工具，而是尝试把公开内容和个人收藏管理放到同一产品中。
2. 确定了“Bangumi 主数据 + MAL 补充字段 + 本地数据库统一读取”的长期数据方向。
3. 已有收藏、追番日历、作品详情、个人资料和 AI 助手等可组合的产品模块。
4. Web 请求优先读取本地数据，Bangumi API 主要用于同步和后台补全，这一边界有利于稳定性和隐私控制。
5. 已开始处理跨来源 ID、canonical 条目、字段来源和增量更新等真实数据工程问题。

## 3. 主要问题

### 3.1 项目仍有明显的拼装痕迹

AniNexus 同时继承了 OtakuNeko 的大量前端模块和 `search_manga` 的 MAL 数据，又新增了首页、详情、认证、推荐和统一后端。各阶段代码尚未完全收束：

- LobeHub UI、Ant Design、Tailwind 和大段自定义 CSS 并存。
- 部分旧前端服务仍然保留，但当前后端未必提供对应能力。
- 一些组件仍承担过多状态、布局和数据转换职责。
- 不同页面的完成度、视觉语言和错误处理方式不一致。

当前更需要统一边界、删除死代码和拆分深层模块，而不是继续增加页面。

### 3.2 文档设计领先实现过多

仓库已经存在 OAuth、RAG、推荐、数据迁移、字段来源和自动同步等详细设计，但以下基础能力尚未完成：

- Bangumi 后台增量更新；
- 多用户 Bangumi OAuth；
- 正式数据库迁移和回滚机制；
- Bangumi/MAL canonical 字段融合；
- 公共日历缓存和降级；
- 完整、可信的播出时间数据。

设计文档应继续保留，但需要明确区分“已实现”“施工中”和“远期设想”，避免文档给出高于实际能力的成熟度预期。

### 3.3 日历界面精度高于数据精度

追番日历支持拖拽、缩放、导入和导出，但 Bangumi Calendar 主要提供星期信息，当前精确到 20 分钟的展示并不总有可信播出时间支撑。

界面显示越精确，用户越容易把推导值误认为官方数据。后续必须记录时间来源，并对估算、默认值和官方时间使用不同标识。

### 3.4 AI 功能建设早于数据地基

AI 助手真正产生差异化价值，需要以下前提：

- 用户收藏能够可靠、增量、按用户隔离地同步；
- 作品、人物、标签和关联关系足够完整；
- 推荐结果可解释且能够追溯数据来源；
- 私人收藏不会无条件发送给外部模型。

在这些前提完成前，继续扩展 RAG、长期记忆、角色和模型选择，容易形成“聊天界面完整，但回答质量没有形成壁垒”的结果。

### 3.5 自研认证带来长期安全责任

当前密码哈希、图片验证码和服务端 Session 已形成基础认证闭环，但公开部署还需继续考虑：

- 登录限流和暴力破解防护；
- 密码重置与身份验证；
- CSRF、防会话固定和会话吊销；
- 多设备会话管理；
- Bangumi OAuth 账号绑定与解绑；
- 审计日志和管理员权限。

自研认证可以用于个人部署，但若目标是公开多用户服务，应持续评估维护成本和安全边界。

## 4. 建议冻结的功能

在核心链路稳定前，建议暂停新增以下能力：

- RAG 和长期记忆；
- RSS/qBittorrent 集成；
- 更复杂的 AI 角色系统；
- 新的数据导入来源；
- 更多首页视觉特效；
- 非必要的日历高级交互；
- 尚无明确用户场景的设置项和管理面板。

冻结不代表删除现有设计或代码，而是暂时停止横向扩张。

## 5. 建议优先完成的黄金路径

下一阶段只围绕以下链路开发：

> 注册登录 → 绑定 Bangumi → 同步收藏 → 浏览本地作品库 → 加入追番日历 → AI 基于本地收藏回答

### 第一阶段：数据与迁移可靠性

1. 建立正式数据库迁移、备份和回滚机制。
2. 完成 Bangumi/MAL 映射感知的 canonical 字段融合。
3. 导入尚未进入目录的 Bangumi 动画，并处理歧义匹配。
4. 为字段、评分、封面和播出时间记录来源与更新时间。
5. 实现可重复运行、可去重、可审计的增量更新任务。

### 第二阶段：用户同步闭环

1. 完成按用户隔离的 Bangumi OAuth。
2. 实现收藏的首次同步和后续增量同步。
3. 明确解绑、Token 失效和上游失败时的行为。
4. 确保收藏、日程和提醒始终引用 canonical `subject_id`。

### 第三阶段：核心体验收敛

1. 统一首页、详情、收藏和日历的视觉语言。
2. 删除无后端支持的前端残留功能。
3. 拆分过大的页面和组件，统一数据访问与错误处理。
4. 对缺失、估算和过期数据提供明确 UI 状态。

### 第四阶段：有限开放 AI

1. 只开放能够由本地结构化数据可靠回答的工具。
2. 为推荐结果提供原因、来源和无法回答时的降级提示。
3. 验证所有工具只能访问当前登录用户的数据。
4. 在真实查询质量达标后，再评估 RAG 和长期记忆。

## 6. 阶段完成标准

黄金路径达到以下条件后，才建议恢复新功能开发：

- 新用户无需手工修改文件即可完成注册、绑定和首次同步；
- 重复同步不会产生重复作品或收藏；
- 上游暂时不可用时，用户仍能浏览已有本地数据；
- 首页、搜索、详情、收藏和日历使用同一 canonical 作品；
- 数据来源、更新时间和估算状态可被用户理解；
- 数据库升级和失败回滚经过自动化验证；
- 核心前后端测试、生产构建和 Docker 启动检查稳定通过；
- AI 助手能够正确回答一组固定的收藏查询和推荐验收题。

## 7. 最终判断

AniNexus 当前最大的风险不是技术实现能力不足，而是同时保留了太多方向。

如果下一阶段集中完成一条可靠的黄金路径，它有机会从“功能丰富的个人项目”成长为真正可长期使用的产品；如果继续横向增加功能，则很可能长期停留在“每个模块完成约七成，但没有一条核心链路达到完整交付”的状态。
